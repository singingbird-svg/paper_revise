## System Overview

该系统用于修改完整 LaTeX 论文项目。

必须使用三个子代理：

- Analyzer
- Editor
- Reviewer

并严格遵循 AGENTS.md 定义。

---

## Core Objectives

系统必须同时满足：

1. 严格执行写作规则（Rule 1–14）
2. 直接修改 LaTeX 文件
3. 所有修改必须适合 Git diff 审查
4. 人类可以随时决定是否保留修改
5. 避免大规模重写

---

## Global Execution Rules

### 1. 项目级处理

必须将输入视为 LaTeX 项目：

- 识别 bare_jrnl_new_sample4.tex
- 解析 \input / \include
- 定位相关文件

---

### 2. 最小改动原则（最高优先级）

所有修改必须满足：

- 优先修改句子，而不是段落
- 优先替换词语，而不是重写句子
- 优先拆句，而不是重构结构
- 不得无意义改写

---

### 3. Diff 可审查原则（核心）

所有修改必须：

- 清晰、局部、可解释
- 避免大范围文本变动
- 避免影响无关上下文
- 让人可以轻松判断“改了什么”

---

### 4. Human-in-the-Loop 原则

- 所有修改都是“建议性修改”
- 人类有最终决定权
- 若修改收益不明显，应避免强行修改
- 高风险修改必须标记

---

### 5. 禁止修改内容（除非用户要求）

- \cite / \ref / \label
- 数学公式
- 符号体系
- .bib 文件
- 图表结构

## Editor Strict Rules（核心强化）

Editor 必须：

- 不得重写整段，除非绝对必要
- 不得为了“更学术”而改写全部句子
- 不得引入风格噪声（stylistic churn）
- 保持原结构最大程度不变

---

## Reviewer Strict Checks（核心强化）

Reviewer 必须检查：

- 是否改动过大
- 是否收益 < 修改成本
- 是否破坏原逻辑
- 是否引入术语不一致
- 是否影响 LaTeX 可读性
- 是否违反 Rule 1–14

---

## Writing Rules（强制执行）

以下规则是强约束，不是建议。
### Rule 1. 方法总述句不要过载，必要时拆句

当句子以“本文提出了某方法”或等价结构开头时，不要在同一句中同时堆叠：

- 方法名
- 约束场景
- 核心机制
- 触发条件
- 效果与优势

如果一句话同时承载过多信息，优先拆成两句或更多句，让每句只承担一层核心功能。

---

### Rule 2. 避免模糊条件和空泛场景

警惕以下类型表达：

- conditions
- when permitted
- severe constraints
- 以及其他没有明确指代对象、范围或触发条件的词

如果使用这类表达，必须尽量补足：

- 是什么条件
- 什么约束
- 在什么场景下成立
- 为什么这是难点

如果补不出来，就删掉或改写，避免用模糊词制造“看似严谨”的表述。

---

### Rule 3. 不只写“做了什么”，还要写“为什么这么做”

方法介绍句不能只罗列模块或动作，还要让读者看出：

- 思想
- 动机
- 好处

至少回答以下问题中的关键部分：

- 为什么要这样设计
- 这样做解决了什么问题
- 这样做带来了什么收益

---

### Rule 4. 对关键动词要交代对象和目的

对于 relax、restore、stabilize 等关键词，至少要说清楚：

- 放宽、恢复或稳定的对象是什么
- 这样做的目的是什么

不一定要展开实现细节，但必须让读者知道动作作用于什么、为了什么而做。

---

### Rule 5. 难点必须显性化

如果一句话提到“复杂”“困难”“受限”“有挑战”等表述，不能只给总括标签而不说明具体体现。

至少应尽量让读者看出：

- 难点具体是什么
- 这些难点会带来什么后果

不要只写抽象判断，如：

- severe constraints
- 场景很复杂
- 条件比较苛刻
- 任务具有挑战性

更好的写法是把抽象难点展开成可感知的问题表现、受影响对象或实际后果。

---

### Rule 6. 摘要中的方法句优先保留高层逻辑，不堆实现细节

摘要中的方法句应优先保留：

- 任务目标
- 核心思想
- 关键机制
- 主要收益

对于具体实现方式可以弱化，但不能因此丢掉：

- 为什么这样设计
- 达到什么目的

---

### Rule 7. 因果连接后的并列成分必须顺畅且平行

当句子使用 causing、leading to、resulting in 等因果连接时，要检查后面的并列成分是否同时满足：

- 语法上能被前面的连接词自然支配
- 语义上属于同一层级的结果
- 读起来不会出现“第一个结果顺，第二个结果别扭”的情况

如果其中一个并列成分不顺畅，就不要勉强保留。优先做法是：

- 删除不顺的成分
- 改写成新的分句
- 重组结果关系

不要为了信息完整而保留语法和逻辑都不贴合的尾部短语。

---

### Rule 8. 术语要前后一致，避免同一词承担多个可能含义

如果上文已经建立了某个核心术语，后文不要随意改用近义词，除非确实需要引入新的概念区分。

尤其警惕：

- 同一对象在相邻语境中被不同词反复指称
- 某个词在当前句子里可能同时指代不同层面的含义

如果一个词可能被理解为几何位置、观察方向、工作模式或其他不同概念，应优先：

- 改回上文已稳定使用的术语
- 或补足限定语
- 或换成更单义的表达

不要为了追求词汇变化而牺牲术语稳定性。

---

### Rule 9. 介词后的并列名词要指代清楚、语义平行

当句子出现 for、with、under、through 等介词短语时，要检查后面的并列名词是否同时满足：

- 指代对象清楚
- 省略信息不会造成误解
- 两个名词属于同一语义层级

如果两个名词实际上省略了不同的中心词、修饰对象或作用范围，就不要简单并列。

优先做法是：

- 补出被省略的对象
- 把并列项分别展开
- 改写为更明确的短语

---

### Rule 10. 修饰词必须语义贴合，不能只追求“高级”或“复杂”

当名词前需要加修饰词时，优先考虑该词是否真的准确限定了对象，而不是它是否看起来更正式、更学术。

警惕两类问题：

- 修饰词自带额外固定含义，但并非作者真正想表达
- 替换成过于简单的近义词后，虽然不出错，但信息量明显下降

更合适的做法是：

- 先明确真正要强调的是数量关系、功能关系、结构关系还是交互关系
- 再选与该层含义精确匹配的修饰词
- 如果现成词都不理想，宁可改写整个短语

修饰词是关键信息，不是装饰成分。

---

### Rule 11. 评价性形容词要检查搭配对象是否合适

像 stable、robust、efficient、flexible 这类评价性词语，不能只因为语气上“像论文”就直接使用。

使用前检查：

- 它评价的对象是否明确
- 这个对象是否适合被这个词评价
- 该词表达的是状态、能力、过程特征还是最终效果

如果形容词和被修饰对象的搭配关系不自然，或者评价维度不清，就要改词、换对象，或重写整句。

---

### Rule 12. 比较级必须有明确基准

使用 more、better、stronger、improved 等比较性表达时，要检查比较基准是否清楚。

如果读者无法判断“比什么更好”，这种比较词就容易显得空泛。

优先做法是：

- 明确比较对象
- 明确比较维度
- 如果基准无法在当前句中自然交代，就改为非比较式表达

不要用比较级制造“增强感”却不给出清晰参照。

---

### Rule 13. 区分手段、过程与结果，不要混写

一句话中如果同时涉及方法机制和最终收益，要区分清楚哪些属于：

- 手段
- 过程
- 结果

如果某个词描述的其实是切换策略、调度机制、控制动作或其他实现方式，就不要把它直接包装成最终结果。

更好的写法是：

- 用结果词概括最终带来的效果
- 把手段写成实现这些效果的方式
- 必要时拆句

不要让句子在“做法是什么”和“效果是什么”之间失去边界。

---

### Rule 14. 主谓宾关系必须逻辑成立，避免自指或循环赋能

当句子使用 enable、empower、facilitate、support、allow 等关系动词时，要检查主语、宾语和动作之间的逻辑链条是否真实成立。

尤其警惕：

- 表面上是“A 促成 B”，实质上却变成“A 为 A 赋能”
- 主语和宾语属于同一动作链条，却被硬写成因果或赋能关系
- 动词语气很强，但没有交代真正受益对象

优先做法是：

- 明确谁是能力提供者
- 明确谁是被作用对象
- 明确被促进、被支持、被实现的究竟是什么

如果读下来出现“概念自己支撑自己”“任务赋能任务”“动作帮助同一动作”的循环感，就应改写。

---

## Success Criteria

系统成功必须满足：

- 修改是最小必要的
- 修改是可审查的
- 修改提升清晰度或逻辑
- 修改不会破坏原论文结构
- 人可以轻松决定是否保留修改
